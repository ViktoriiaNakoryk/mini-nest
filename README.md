# mini-nest

Навчальний mini-Nest. Частина 1 — IoC-контейнер, який читає метадані типів із конструктора й сам збирає граф залежностей. Частина 2 — HTTP-шар: маршрутизація на декораторах і валідація вхідних даних поверх `node:http`, без Express/Fastify/Nest.

## Як запустити

Встановлення:

```bash
npm install
```

Тести локально:

```bash
npm test
```

Тести в Docker:

```bash
docker compose run --rm api npm test
```

## Як це працює

Коли клас позначений декоратором `@Injectable()`, а в `tsconfig.json` увімкнена опція `emitDecoratorMetadata`, TypeScript під час компіляції автоматично записує типи параметрів конструктора в метадані класу під ключ `design:paramtypes`. `Container.resolve()` дістає цей масив типів через `Reflect.getMetadata('design:paramtypes', Target)` і для кожного типу з масиву рекурсивно викликає `resolve()` знову, і будується весь ланцюжок залежностей, від кореневого класу до найглибшого.

Якщо прапорець `emitDecoratorMetadata` вимкнений, TypeScript узагалі не генерує цих метаданих під час компіляції: виклик `Reflect.getMetadata('design:paramtypes', Target)` поверне `undefined`, і контейнеру нема звідки брати список залежностей.

## HTTP-шар (частина 2)

Декоратори нічого не роблять під час запиту — вони лише під час завантаження класу пишуть записки в метадані. `@Controller('users')` кладе префікс у метадані класу; `@Get(':id')` / `@Post()` додають опис маршруту в масив метаданих класу; `@Body()` / `@Param(name)` / `@Query(name)` описують, який аргумент звідки брати. [`src/router.ts`](src/router.ts) читає ці записки через `Reflect.getMetadata` і будує плоску таблицю маршрутів (жодних захардкоджених шляхів). [`src/dispatcher.ts`](src/dispatcher.ts) поверх `node:http` на кожен запит знаходить рядок таблиці, парсить тіло, збирає аргументи, тягне контролер із контейнера частини 1 (той самий singleton) і викликає метод.

### Як параметр-декоратор знає, куди підставити значення

Параметр-декоратор отримує три аргументи: `(target, propertyKey, parameterIndex)`. Ключове тут — `parameterIndex`: це позиція аргумента у сигнатурі методу (0 — перший аргумент, 1 — другий тощо). Декоратор не витягує жодних даних із запиту — він лише записує в метадані методу мапу `{ [parameterIndex]: { type: 'body' | 'param' | 'query', name } }`. Тобто «аргумент №0 — це `param` з іменем `id`», «аргумент №1 — це `query` з іменем `limit`».

Пізніше, під час реального запиту, диспетчер робить зворотну операцію. Він читає цю мапу і для кожного `index` дивиться на `type`: `body` → розпарсене тіло, `param` → `pathParams[name]`, `query` → `query.get(name)`. Зібрані значення розкладаються в масив `args` рівно за своїми індексами, і метод викликається як `handler(...args)`. Саме завдяки тому, що індекс аргумента — це і ключ у мапі, і позиція у виклику, значення потрапляє точно в потрібний параметр, незалежно від порядку, у якому декоратори були оголошені.

### Валідація DTO

Для `@Body()` з типом DTO диспетчер перед викликом методу проганяє тіло через [`src/pipes/validation.pipe.ts`](src/pipes/validation.pipe.ts): спершу `plainToInstance(Dto, body)`, тоді `validate(instance)`. Перший крок обов'язковий — `class-validator` працює з екземплярами, а не з plain-об'єктами, і без нього мовчки нічого не перевірить. Невалідне тіло → HTTP 400 зі списком `[{ field, constraints }]`; валідне → у метод приходить саме екземпляр DTO (`body instanceof CreateUserDto`).
